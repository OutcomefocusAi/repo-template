# Design: add-openspec-pin-check

## Context

See proposal.md for why. Facts checked on 2026-11-09 against `main` `52e24f9c6b94684f180aa2f3ee1b0e5c26380a3c` (PR #31 squash-merged at 9:14 PM AZ, OpenSpec 1.17.0):

- The nine records and where they sit: `generatedBy: "1.17.0"` on line 10 of each of the six `.agents/skills/openspec-*/SKILL.md` (YAML front matter, under `metadata:`); `npm install --global --no-fund --no-audit @fission-ai/openspec@1.17.0` on line 41 of `.github/workflows/ci.yml` (the only `@fission-ai/openspec@` in any workflow); `TEMPLATE_SOURCE.md` line 20 (Sources row starting ``| `.agents/skills/openspec-*/` |``, text "Generated by `@fission-ai/openspec` 1.17.0") and line 31 (Tool pins row `| @fission-ai/openspec | 1.17.0 | ...`).
- Existing check scripts are Bash with `set -euo pipefail`, `cd "$(git rev-parse --show-toplevel)"`, `::error file=,line=::` annotations, exit 1 on findings and exit 2 on usage errors (`check-workflows.sh`). Each is self-tested in `scripts/test-template-scripts.sh` through `expect <exit> <name> in_repo <cmd>` against a scratch git repository that copies `scripts/` and `.github/workflows/`; fixtures are made by copying and editing files there.
- Ponytail records on `52e24f9`: each of `.agents/skills/ponytail/`, `ponytail-review/` and `ponytail-audit/` has a `SOURCE.md` table with `| Pinned commit | \`96608e078b2d5ea607c5c3b8b5a54d1c1fba6846\` |` (line 9), `| Upstream version | ... (\`git describe --tags\`: \`v5.3.3-1-g96608e0\`) |` (line 10), `| File at that commit | https://github.com/DietrichGebert/ponytail/blob/<sha>/skills/<name>/SKILL.md |` (line 11), and `| SHA-256 of \`SKILL.md\` |` and `| SHA-256 of \`LICENSE\` |` (lines 15 and 16). All six recorded SHA-256 values equal `sha256sum` of the files on disk. `TEMPLATE_SOURCE.md` line 19 is the only Ponytail row (Sources table; there is no Tool pins row): ``| `.agents/skills/ponytail/`, `ponytail-review/`, `ponytail-audit/` | https://github.com/DietrichGebert/ponytail at `<sha>` (`v5.3.3-1-g96608e0`), MIT, vendored 2026-11-03; ...``.
- No `SOURCE.md` records the OpenSpec version (only the three Ponytail folders have one), and `README.md` and `AGENTS.md` name no OpenSpec version.

## Goals / Non-Goals

**Goals:**
- CI fails, naming file and line, whenever the nine OpenSpec records disagree, one is missing or duplicated, or one is not an exact version.
- CI fails, naming file and line, whenever a Ponytail `SOURCE.md` and the `TEMPLATE_SOURCE.md` Ponytail row disagree on the commit or `git describe` string, a commit is not a full SHA, a record is missing, or a vendored `SKILL.md` or `LICENSE` no longer matches its recorded SHA-256.
- Both checks are version-agnostic, so a version-only bump that updates all records passes with no script change.

**Non-Goals:**
- Checking that the pinned version is the newest on npm (that is Chief of Staff's weekly drift check).
- Fetching upstream. The Ponytail check compares records with each other and with files on disk; whether the pinned commit is upstream's newest, or whether the files equal upstream at that commit, stays with the weekly drift check and the update procedure in each `SOURCE.md`.
- The "Date vendored" values and the folder list in the `TEMPLATE_SOURCE.md` row (see Decision 4).
- Changing any pin or the generated skills.

## Decisions

1. **One small script per record family, starting with `scripts/check-openspec-pin.sh`, each run as its own CI step.** Same shape as `check-workflows.sh`, so the step name in the CI log says exactly what failed. Alternatives: a case inside `test-template-scripts.sh` that inspects the real tree (rejected: the self-test is for testing scripts, and a drift failure would hide among some 80 cases), or a step in `install-ci-tools.sh` (rejected: that script installs tools and has nothing to do with the template's records).
2. **Extraction rules (each anchored to the record's own syntax, read with `grep -n` so errors carry a line):**
   - Skills: every `.agents/skills/openspec-*/SKILL.md` must have exactly one indented `generatedBy:` line; the value is taken with or without quotes. At least one skill folder must exist. The count is not fixed at six, so a future `openspec update` that adds or removes a skill does not need a script change.
   - CI: every `@fission-ai/openspec@<version>` in `.github/workflows/*.yml`; at least one must exist. Scanning all workflows catches a second install line added later.
   - `TEMPLATE_SOURCE.md`: exactly one Sources row starting ``| `.agents/skills/openspec-*/` |`` (version after "`@fission-ai/openspec` ") and exactly one Tool pins row starting `| @fission-ai/openspec |` (second column).
   - Each value must match `^[0-9]+\.[0-9]+\.[0-9]+$`. A pre-release or range is rejected; AGENTS.md requires exact pins.
   - Agreement: all values equal. On disagreement the script uses the `ci.yml` pin as the reference (it is what CI actually installs) and prints one error per record that differs, with file, line and both versions, followed by the full list of records.
3. **Scenario goes in `continuous-integration`, not `agent-guidance`.** The `agent-guidance` scenario "OpenSpec pin records agree" already states the rule; what is new is that CI enforces it, and "Template checks always run" in `continuous-integration` is where every other CI check is listed. The MODIFIED block copies the whole requirement, adds clauses to its description (443 characters, under the 500 limit) and four scenarios (two OpenSpec, two Ponytail). The `agent-guidance` text stays as it is.
4. **Ponytail pins: a separate script, `scripts/check-ponytail-pin.sh`, not a combined `check-pins.sh`.** Woody's approval added this to #32. Keeping two scripts leaves `check-openspec-pin.sh` exactly as proposed at `c4825ab` (name, records, output), gives each its own CI step so the log says which family drifted, and keeps each script short and single-purpose like the other `check-*.sh`. The alternative, one `check-pins.sh` with both families, would save one step and some boilerplate (about 10 shared lines) but change the approved OpenSpec check's name and mix two unrelated record formats in one script. Rules:
   - Folders: every `.agents/skills/ponytail*/` directory; at least one must exist, and each must have a `SOURCE.md`.
   - Commit: in each `SOURCE.md`, exactly one `| Pinned commit |` row whose value is a full lowercase 40-hex SHA, and exactly one `| File at that commit |` row whose URL contains `/blob/<same sha>/`. In `TEMPLATE_SOURCE.md`, exactly one Sources row starting ``| `.agents/skills/ponytail/` ``, whose commit is the 40-hex value after "at `". All must be equal; the `TEMPLATE_SOURCE.md` row is the reference, and each differing record gets its own error.
   - `git describe` string: the backticked `v...` token in each `SOURCE.md` "Upstream version" row and in the `TEMPLATE_SOURCE.md` row (the token in "(`v...`)"); all must be equal.
   - Fingerprints: for each folder, the `| SHA-256 of \`SKILL.md\` |` and `| SHA-256 of \`LICENSE\` |` values (64-hex) must equal `sha256sum` of those files. This is cheap and unambiguous (a local hash compared with a recorded hash), and it catches an edit to a vendored file, which `AGENTS.md` forbids. It does not prove the files equal upstream; it proves they equal what `SOURCE.md` says was vendored.
   - Not checked: "Date vendored" (a date mismatch has no effect on what is run, and a same-day re-vendor would make it noisy) and whether the `TEMPLATE_SOURCE.md` row names every folder (prose list, not a record). Both can be added later if drift shows up there.
5. **Order in CI: "OpenSpec pin agreement" then "Ponytail pin agreement", right after "Em-dash check".** All three are cheap static checks on the tree; failing early saves the gitleaks and OpenSpec validation time. Neither depends on the installed OpenSpec version.
6. **Spec placement for Ponytail too.** The Ponytail scenarios go in the same `continuous-integration` requirement as the OpenSpec ones, for the same reason as Decision 3; the `agent-guidance` scenario "Pin records agree" keeps stating the rule.

## Risks / Trade-offs

- [The row formats in `TEMPLATE_SOURCE.md` change] → The check then fails with "expected one ... row", which is the intended signal; the self-test covers the missing-row case, and the error says which row to restore.
- [A derived repository edits `TEMPLATE_SOURCE.md` or regenerates skills at another version without updating all records] → CI fails there, which is the point. The error names each record so the fix is mechanical.
- [A Ponytail update forgets to refresh a SHA-256 in `SOURCE.md`] → The check fails with the file and both hashes; the update procedure in `SOURCE.md` step 5 already says to refresh them.
- [Line endings or a stray edit to a vendored file] → The fingerprint check fails; restore the upstream bytes rather than updating the hash, as `SOURCE.md` says not to edit the copies.
- [`openspec update` changes how it writes `generatedBy` (for example drops the quotes)] → The extraction accepts quoted and unquoted values; any other format change fails loudly, and the weekly bump PR would show it.
- [Workflow file edit] → The pull request runs its own `qa-gate` copy; QA checks the one-step diff in `ci.yml`, and `check-workflows.sh` and actionlint still pass.
